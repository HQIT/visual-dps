### 架构结论（延迟分层）

```text
WebRTC 预览（快，~实时）
        ≠ 画面内容时刻
RTSP → 推理(~32ms) → pose → worker(~0.3ms) → SSE → 前端骨架/碰撞 overlay
        ↑ 稳态 pipeline ~70–80ms          ↑ 尖峰时 +数秒（LiveHub JSONL）
```

- **体感 ~1s**：主要来自 **WebRTC vs RTSP 内容差**，不是 infer 单段慢。
- **overlay 内部一致**：骨架与碰撞同源 pose，`skeleton_source=pose` 100%，`frame_idx_delta=0`。

### 4.1 连续 HIT 无 ALARM（已定位根因，待修代码）

**现象**（`test_camera`，`COLLISION_LOG=1`，`alarm_min_consecutive_frames=3`，`alarm_cooldown_frames=0`）：

- 352–358、112–120 等时段：**多帧连续 `[COLLISION][HIT] hits=['shelf1:1']`，全程无 `[ALARM]`**。
- 同一会话稍后（如 frame 757、769）：**第 3 帧 HIT 后出现 ALARM**，门控参数本身有效。

**日志时间线（同一 event-worker 容器，未 restart worker）**：

| 墙钟 | frame | video_time | 日志 |
|------|-------|------------|------|
| 12:59:43 | **784** | 52.2s | `[HIT]` + `[ALARM]` shelf1:1 |
| 13:10:45 | **66** | 4.3s | 仅 `[HIT]`（**infer 已重启**，frame_idx 回绕） |
| 13:10:45–55 | 66→**120** | 4.3→7.9s | **连续 55+ 帧 HIT，0 条 ALARM** |

**根因**：`CollisionProcessor` 用 **绝对 `frame_idx`** 做冷却门控，状态存在 **event-worker 进程内存** 中，**infer 重启后不会清空**。

```python
# services/event_engine/collision.py
if (
    self._box_consecutive_hits[token] >= self.alarm_min_consecutive_frames
    and frame_idx - last_alarm >= self.alarm_cooldown_frames  # last_alarm 为上一轮 infer 的 frame
):
    alarm_collisions.append(token)
    self._box_last_alarm_frame[token] = frame_idx
```

- 上一轮在 frame **784** 告警 → `_box_last_alarm_frame['shelf1:1'] = 784` 残留。
- 新 infer 从 frame **66** 重新计数；`alarm_cooldown_frames=0` 时条件等价于 **`frame_idx >= last_alarm`**。
- 新 session 中 frame 114：`114 - 784 = -670 < 0` → **ALARM 被静默挡住**；HIT 仍每帧输出（不受此门控影响）。
- 需新 session 的 `frame_idx` 再次 ≥784（约 video_time 52s）才会恢复 ALARM，或 **restart event-worker** 清空状态。

**与 HIT / ALARM 语义区分**：

| 类型 | 条件 | infer 重启后 |
|------|------|--------------|
| HIT | 当前帧手腕在 ROI | 正常 |
| ALARM | 连续 N 帧 HIT **且** `frame_idx - last_alarm >= cooldown` | 可能长期失效 |

**临时规避**：

```bash
# 停启 infer 前/后 restart worker，清空 _box_last_alarm_frame
docker restart visual-dps-event-worker
```

**建议代码修复**（待合入）：

1. 检测 **`frame_idx` 回退**（`frame_idx < _last_seen_frame_idx`）时重置 `_box_last_alarm_frame` / `_box_consecutive_hits`。
2. 或 pose 携带 **infer session / run_id**，session 变化时 reset processor 告警状态。
3. 冷却改为 **相对连续计数**，不依赖跨 session 的绝对 frame_idx。

### 4.3 `pose_frame_interval` 双重 sleep 导致 pose 率偏低（已修复并验证）

**修复前现象**（`test_camera`，`frame_rate=15`，碰撞日志 `time` 墙钟差 vs `video_sec`）：

| `pose_frame_interval` | 配置 pose 上限 | 修复前实测（墙钟） | 2 帧 ALARM 墙钟 |
|----------------------|----------------|-------------------|-----------------|
| **1** | 15 fps / **67 ms** | **~67 ms** ✓ | ~72 ms |
| **2** | 7.5 fps / **133 ms** | **~200 ms**（~5 fps） | ~208 ms |
| **3** | 5 fps / **200 ms** | **~334 ms**（~3 fps） | ~347 ms |

**修复后验证**（`alarm_min_consecutive_frames=2`，`COLLISION_LOG=1`，重启 infer 后）：

| `pose_frame_interval` | 配置目标 | 修复后实测 Δtime | 日志摘录 |
|----------------------|----------|------------------|----------|
| **2** | **133 ms** | **135 ms** ✓ | frame 30 `14:52:58.100` → frame 31 `14:52:58.235` |
| **3** | **200 ms** | **204 ms** ✓ | frame 29 `14:55:43.632` → frame 30 `14:55:43.836` |

```text
# interval=2（7.5 fps）
[COLLISION][HIT] time=2026-07-02 14:52:58.100 ... frame=30 ...
[COLLISION][HIT] time=2026-07-02 14:52:58.235 ... frame=31 ...
[COLLISION][ALARM] time=2026-07-02 14:52:58.235 ... frame=31 ...

# interval=3（5 fps）
[COLLISION][HIT] time=2026-07-02 14:55:43.632 ... frame=29 ...
[COLLISION][HIT] time=2026-07-02 14:55:43.836 ... frame=30 ...
[COLLISION][ALARM] time=2026-07-02 14:55:43.836 ... frame=30 ...
```

- **135 ms vs 133 ms**、**204 ms vs 200 ms**：误差在 infer 循环抖动内，与 **N×67 ms** 对齐。
- **比例**：204 / 135 ≈ 1.51 ≈ 3/2，符合 interval 倍数关系。
- **`video_sec` 步长**仍为 **67 ms**（15 fps 的 frame 索引），与 interval 无关；墙钟 pose 间隔用 **Δtime** 衡量。

- **interval=1 能跑满 15 fps**：JSONL `infer_loop` p50 ~33 ms，单轮算力足够；墙钟 Δtime ≈ Δvideo_sec（67 ms）。
- **interval≥2「跑不满」不是 GPU 算不动**：同一模型在 interval=1 已证明可在 **67 ms** 内完成一轮 pose；偏慢来自 **主循环 pacing 实现**，非 rtmpose_m 算力瓶颈。

**相关代码**（`services/inference_service.py`，headless RTSP infer）：

```python
# 修复前（headless pose tick 末尾，与 skip sleep 叠加）
pose_period = frame_period_sec * pose_frame_interval
sleep_sec = pose_period - elapsed_loop

# 修复后（c56d99b）：pose tick 仅睡 1 tick；skip tick 仍 sleep_skip = frame_period - elapsed
sleep_sec = frame_period_sec - elapsed_loop
```

**根因**：两种 pacing **各自合理，但不应同时存在**：

| 逻辑 | 含义 | 单独使用 |
|------|------|----------|
| **A — skip 睡 67 ms** | 主循环按 15 tick/s 网格推进 `inference_tick` | ✓ |
| **B — pose tick 睡 interval×67 ms** | 出 pose 那拍按 **N/15 s** 限速 | ✓ |
| **A + B 叠加（现状）** | skip 累计 **(N−1)×67 ms** + pose **N×67 ms** | ✗ |

两帧 pose 之间墙钟（推理较快、sleep 睡满时）：

\[
T_{\text{实际}} = (N-1)\times\frac{1}{15} + N\times\frac{1}{15} = \frac{2N-1}{15}\ \text{s}
\]

| N | 配置目标 \(N/15\) | 实际 \((2N-1)/15\) | 实测（碰撞日志） |
|---|-------------------|---------------------|------------------|
| 2 | 133 ms | **201 ms** | ~208 ms |
| 3 | 200 ms | **335 ms** | ~347 ms |

**与告警门控的关系**：`alarm_min_consecutive_frames=2` 时，首 HIT→ALARM 墙钟 = **1 个 pose 间隔**（两帧连续 HIT 同拍 ALARM）。修复前 interval=2 实测 ~208 ms（应为 133 ms）；修复后 **135 ms**，与 pose pacing 一致（非 worker 问题）。

**配置链路**：`runtime_config.json` → `inference_container_service` 注入 `INFERENCE_FRAME_RATE` / `INFERENCE_POSE_FRAME_INTERVAL` → `inference_worker._apply_inference_env_overrides` → `InferenceService` 读 `app_config.inference`。

**修复**（§4.3，**已合入并验证 2026-07-02**）：保留 **skip tick 睡 `frame_period`**；pose tick 末尾 **仅睡 1 个 tick**（`frame_period − elapsed`），**不再乘** `pose_frame_interval`。改动 `services/inference_service.py` 循环末尾 sleep；bind mount 生效后 **重启 infer** 即可。

修复后两帧 pose 墙钟：\((N-1)\times\frac{1}{15} + \frac{1}{15} = \frac{N}{15}\) s，与配置 **15/N fps** 一致。

**其它本日日志改进**：

- `services/wall_clock.py`：`time=` 墙钟已改为 **毫秒**（`YYYY-MM-DD HH:MM:SS.mmm`），便于碰撞日志算 Δtime。
- 碰撞日志：`time`（墙钟） vs `video_sec`（片内 `frame_idx/fps`）**不应混减**；真实间隔用 **Δtime**，片内步进用 **Δvideo_sec**。
